# 第三幕 · 决策（Decide）——MVP 边界划在哪？什么进什么不进？

> **本幕目标**：在资源、时间、风险三重约束下，从一堆"都重要"的需求里切出 MVP 的边界。本幕调度理论的总原则——**对的优先级方法 = 对的问题 + 对的指标 + 对的精度**：Kano 回答"用户视角的必要性"，RICE/ICE 回答"投入产出比"，MoSCoW 回答"承诺等级"，北极星指标回答"什么方向"。**任何单一方法都会带来系统性偏见**，必须组合校准。

---

## Kano 模型 / 五种需求分类

**一句话定义**：把功能按"满足度 vs 用户兴奋度"的非线性关系分成 5 类——必备、期望、兴奋、无差异、反向——决定投资重心。

**出处**：狩野纪昭（Noriaki Kano）等 1984 年发表于《Quality》杂志的"Attractive Quality and Must-be Quality"。源于质量管理领域，被产品管理借用。

**适用情境（默认场景）**：
- 功能列表很长且团队对"重要性"打架时
- 想识别"做了也没用 / 不做就死 / 做了惊艳"的功能差异时
- 跨品类竞品分析（同样的功能在不同品类的 Kano 属性可能完全不同）
- 防止过度投资"已经是 must-be 的功能"——再做再好用户也不感谢

**核心步骤**：
1. **列功能候选**：从 PRD / 用户反馈 / 竞品分析收集 15-30 个功能
2. **设计 Kano 问卷**：每个功能问两个问题——"如果有这个功能你感觉如何？" + "如果没有这个功能你感觉如何？" 答案选项：①很喜欢 ②理应如此 ③无所谓 ④勉强接受 ⑤很不喜欢
3. **答案配对查 Kano 矩阵**：得到该功能的属性（M=必备 / O=期望 / A=兴奋 / I=无差异 / R=反向）
4. **统计每个功能的众数属性 + 计算 Better/Worse 系数**（Better = (A+O)/(A+O+M+I)，Worse = -(O+M)/(A+O+M+I)）
5. **决策**：M 是底线（必做但别过度）；O 投入产出线性（值得做好）；A 是差异化（做对了爆款，做错了浪费）；I 砍掉；R 反向砍掉

**局限与不适用**：
- **属性会随时间漂移**：今天的 A（兴奋）三年后变成 M（必备）——iPhone 的多点触控就是案例。**不能一次问完用三年**
- **不适用于全新品类**：用户没用过的功能问"有/没有"都无法准确回答
- **样本量要求高**：每个功能至少 30-50 个有效问卷才能稳定分类，小团队做不起
- **B 端场景失效**：B 端决策人 vs 使用人对同一功能的 Kano 属性常常相反，需要分角色问卷
- **常见误用**：把所有功能都放到一张 Kano 图上 → I 类多得淹没其他，应先用 RICE/ICE 粗筛

**与其他理论的配合**：
- **上游配合**：HMW + 头脑风暴 → 输出功能候选清单；JTBD → 提供"Job 视角下哪些是必备"的预判
- **下游配合**：Kano 的 M 类 → 喂给 MoSCoW 的 Must；A 类 → 喂给 MoSCoW 的 Should；I/R 类 → 喂给 MoSCoW 的 Won't；A 类的 Better 系数 → 喂给 ICE 的 Impact
- **互替**：MaxDiff 在"重要性排序"上更精确但缺少"必备/兴奋"的分类视角；Conjoint Analysis 适合涉及权衡（trade-off）的功能组合

**判断要点（融会贯通信号）**：
- 当团队为"砍不砍某功能"争执——Kano 的 I 类判定能直接终止辩论
- 当产品长时间没新意但功能一直加——多半 A 类没投入，全在 M 类做边际优化

**示例输出片段**：
> **B 端 AI 报表工具 Kano 分析（部分）**
> ┌───────────────────┬───┬────────┬────────┬─────────┐
> │ 功能              │ 属性 │ Better │ Worse  │ 决策    │
> ├───────────────────┼───┼────────┼────────┼─────────┤
> │ 多源数据接入      │ M │ 0.32   │ -0.78  │ 必做基线│
> │ 自然语言生成 SQL  │ A │ 0.81   │ -0.12  │ 重投差异│
> │ 老板风格模板库    │ A │ 0.74   │ -0.18  │ 重投差异│
> │ 高级图表样式自定义│ I │ 0.21   │ -0.08  │ 砍/延后 │
> │ 跨企业基准对比    │ R │ -0.31  │ -0.42  │ 反向砍  │
> └───────────────────┴───┴────────┴────────┴─────────┘

## RICE 优先级评分

**一句话定义**：用 Reach × Impact × Confidence ÷ Effort 给每个功能打一个可比较的"价值密度"分数。

**出处**：Sean McBride / Intercom 团队在 2016 年公开化（Intercom Blog: "RICE: Simple prioritization for product managers"）。后被广泛采纳为标准产品优先级框架。

**适用情境（默认场景）**：
- 中大型产品 Roadmap 排期，需要在 20+ 候选中选 5-10 个
- 跨团队协作场景，需要一个客观可比较的分数防止"嗓门大的赢"
- 季度 OKR 拆解后选 Initiative
- 不同类型功能混排（增长功能 vs 体验优化 vs 技术债）

**核心步骤**：
1. **Reach（触达数）**：每季度/月该功能能影响多少用户——用绝对数字，不要用百分比
2. **Impact（每用户影响）**：定量打分 0.25 / 0.5 / 1 / 2 / 3（最小/低/中/高/巨大），不要自定义连续数
3. **Confidence（信心度）**：100%（有数据）/ 80%（有逻辑论证）/ 50%（直觉）/ 20%（瞎猜）——必须配证据
4. **Effort（投入）**：人·月或人·周——必须包含设计+研发+测试+运营，不能只算开发
5. **计算 RICE = R × I × C ÷ E**，从高到低排序，画"分数 vs 投入"散点图找性价比甜区

**局限与不适用**：
- **Impact 打分主观性大**：5 档离散值无法反映"中等偏上"——容易陷入"我觉得是 2 你觉得是 1"的扯皮
- **Confidence 80% 的陷阱**：团队倾向给所有功能 80%——必须用证据 anchor，没数据强制降到 50% 以下
- **不适用于战略级决策**：RICE 是战术工具，"要不要进入 AI 赛道"这种问题用 RICE 算是僭越
- **对"无法量化 Reach 的体验型功能"失效**：比如"提升品牌质感"——Reach 怎么算？此时应改用 ICE 或 Kano
- **不区分功能间的依赖关系**：A 功能 RICE 高但必须先做 B，单纯排序会漏掉这层结构

**与其他理论的配合**：
- **上游配合**：Kano 的 A 类候选 → 喂给 RICE 评估投入产出；Lean Canvas 的 Solution 候选 → 喂给 RICE
- **下游配合**：RICE Top N → 喂给 MoSCoW 做承诺等级；RICE 分数 → 喂给 Story Mapping 决定 Release 切片
- **互替**：ICE 是 RICE 的简化版（去掉 Reach），更适合早期；Weighted Scoring 可以自定义维度更灵活；Cost of Delay 适合时间敏感型决策

**判断要点（融会贯通信号）**：
- 当 Roadmap 候选 >10 个 且团队意见分裂——RICE 提供共同语言
- 当每个功能 Confidence 都标 80%——立即停手，强制做证据回溯

**示例输出片段**：
> **RICE 评分（季度 Roadmap）**
> ┌──────────────────────┬──────┬──────┬──────┬──────┬──────┐
> │ 功能                 │ R    │ I    │ C    │ E    │ RICE │
> ├──────────────────────┼──────┼──────┼──────┼──────┼──────┤
> │ 自然语言生成 SQL     │ 2000 │ 3    │ 80%  │ 8w   │ 600  │
> │ 老板风格模板库       │ 2000 │ 2    │ 80%  │ 3w   │ 1067 │
> │ 多源数据接入(SAP)    │ 600  │ 3    │ 50%  │ 12w  │ 75   │
> │ 移动端 App           │ 1200 │ 1    │ 50%  │ 16w  │ 38   │
> └──────────────────────┴──────┴──────┴──────┴──────┴──────┘
> **决策**：模板库性价比最高优先做；自然语言 SQL 投入大但 Impact 巨大值得；多源 SAP 接入 Confidence 太低，先验证再投入；移动端这季度砍掉。

## MoSCoW 优先级

**一句话定义**：把功能按"承诺等级"分成 Must / Should / Could / Won't 四档，用于团队对外的交付承诺管理。

**出处**：Dai Clegg 在 Oracle 1994 年提出，作为 DSDM（Dynamic Systems Development Method）的标准优先级工具。后被 Agile / Scrum 社区广泛采纳。

**适用情境（默认场景）**：
- Sprint / Release 范围对齐——告诉团队和老板"这次到底交付什么"
- 与外部客户/上游谈判 SOW（Statement of Work）时的合同语言
- 资源紧张时的"防止 scope creep 的护栏"
- 跨团队依赖项管理（"我们的 Should 是你们的 Must"）

**核心步骤**：
1. **Must Have**：不做产品就不可用 / 法律合规要求 / 用户核心 Job 必备——通常占 60% 以内
2. **Should Have**：重要但缺了产品还能用 / 第一时间会被反馈但不阻塞——占 20%
3. **Could Have**：锦上添花 / 资源富余时做——占 20%
4. **Won't Have (this time)**：明确这次不做——必须显式列出，避免后续被偷塞进来
5. **总量校验**：Must 不能超 60% 工作量——超了说明 Must 滥用，重新分类

**局限与不适用**：
- **Must 极易滥用**：所有 stakeholder 都说自己的需求是 Must，需要强制 60% 上限
- **不适用于"价值不可比"的功能集**：MoSCoW 不告诉你 A 和 B 哪个 ROI 高，只告诉你承诺等级——所以必须先用 RICE/ICE 排序再分级
- **Won't 容易被忘记**：必须公开记录并定期回顾，否则下个版本又被悄悄塞回来
- **不适用于纯探索型项目**：还没有明确"交付承诺"的项目用 MoSCoW 是过度结构化
- **常见误用**：把 MoSCoW 当成"重要性排序"——它不是，它是"承诺等级"

**与其他理论的配合**：
- **上游配合**：RICE/ICE 排序结果 → 喂给 MoSCoW 做分级；Kano 的 M 类 → 强约束进 MoSCoW 的 Must
- **下游配合**：MoSCoW Must/Should → 喂给 Sprint Planning 和 Story Mapping 的当前 Release；Won't → 进入 Backlog 但显式标注
- **互替**：Priority Levels（P0/P1/P2/P3）几乎等价但缺少"显式 Won't"的语义；MVP/MMP/MLP 分级在范围上更宏观

**判断要点（融会贯通信号）**：
- 当对外要给出"这次到底交付什么"的承诺——MoSCoW 是合同语言
- 当 Must 列表超过工作量 60%——MoSCoW 滥用，立即重新分级

**示例输出片段**：
> **MoSCoW（v1.0 MVP，Q3 交付）**
> Must（70w 工作量上限）：自然语言生成 SQL ✓ / 多源数据接入(3 主流 ERP) ✓ / 报表导出 PDF/Excel ✓ / 用户权限管理 ✓
> Should：老板风格模板库（10 个起步）/ 报表订阅推送 / 错误数据高亮提示
> Could：模板社区分享 / 移动端预览
> **Won't (this time)**：高级建模 / 跨企业基准 / 自定义图表代码 / 移动端编辑
> ——明确"Won't"是为了防止销售在客户面前承诺导致返工

## 北极星指标 / North Star Metric

**一句话定义**：选一个"既反映用户获取的价值，又预测公司长期增长"的核心指标作为团队对齐方向的唯一聚光灯。

**出处**：Sean Ellis（增长黑客之父）2017 年系统化提出；Amplitude《The North Star Playbook》是当前最完整的实践指南。核心思想根源可追溯到 Andy Grove 在 Intel 的高产单一指标管理。

**适用情境（默认场景）**：
- 公司/产品需要团队对齐唯一方向时
- 跨团队 OKR 拆解的顶层锚点
- 决策评估的"试金石"——任何决策都问"这是否服务于北极星"
- 防止陷入"虚荣指标"陷阱（DAU/曝光等不反映价值的数字）

**核心步骤**：
1. **识别价值时刻**（Aha Moment）：用户什么时候开始觉得"这产品真有用"
2. **写一句话定义北极星**：必须包含"用户做了 X 行为 + 反映价值 + 可量化频率"
3. **拆 Input Metrics**（输入指标）：通常 3-5 个，每个负责北极星的一个组成部分（广度×深度×频率×效率）
4. **检验四个标准**：①反映客户价值 ②表征长期增长 ③可衡量 ④可被团队行动影响
5. **设守护指标**（Guardrail Metric）：防止单一指标被"作弊式优化"（比如北极星=订单量，守护=退货率）

**局限与不适用**：
- **0→1 阶段定不准**：还没找到 PMF 就强行定北极星 = 锚错方向，应先用 AARRR 多指标观察
- **平台型/多边市场**：单一北极星可能掩盖某一边的健康度，需要每边一个北极星
- **容易选成"领先指标"或"滞后指标"陷阱**：选 DAU 太领先（不反映价值），选 ARR 太滞后（反馈太慢）——要选"价值发生频率"
- **常见误用**：把北极星等同于商业指标（GMV/收入）——这是滞后指标，不是真北极星
- **指标选错的代价巨大**：所有团队会"用力一处"，错的方向会让整个组织偏航

**与其他理论的配合**：
- **上游配合**：JTBD 的核心 Job 完成度 → 喂给北极星定义；VPC 的核心价值 → 锚定北极星方向
- **下游配合**：北极星 → 喂给 HEART 框架做体验拆分；喂给 AARRR 做漏斗诊断；喂给 RICE 的 Impact 维度
- **互替**：OMTM（One Metric That Matters）几乎等价，更强调"当下阶段"的灵活替换；Aha Metric 是北极星的简化版（只看激活）

**判断要点（融会贯通信号）**：
- 当团队对"做这个值不值得"反复争论——多半因为没有共同的北极星
- 当所有人都喊"用户增长"但谁也说不清"用户的价值是什么"——立即北极星会议

**示例输出片段**：
> **北极星指标（B 端 AI 报表工具）**：周活专员中"完成 ≥ 3 份老板满意报表"的人数
> **拆解 Inputs**：
> ①广度：周活专员数 ②深度：人均完成报表数 ③效率：单报表平均生成时长 ④质量：报表被老板"通过"的比例
> **守护指标**：①报表数据准确率（防止"快但错"） ②客户 NPS（防止用户讨厌但被 KPI 推着用）
> **决策检验**：任何新功能问——它能让上述北极星变好吗？说不清就别做。

## ICE 快速打分

**一句话定义**：用 Impact × Confidence × Ease 三个维度快速打分，是 RICE 的轻量版，适合早期高速决策。

**出处**：Sean Ellis 在 GrowthHackers 社区推广，作为 Growth Experiment 的标准排序工具。

**适用情境（默认场景）**：
- 增长实验排期（每周/双周大量小实验需要排序）
- 早期产品（用户量少，Reach 不显著差异，RICE 退化为 ICE）
- 设计/营销/运营创意排序（Impact 难精确量化时）
- 黑客松/快速原型阶段的决策

**核心步骤**：
1. **Impact**：1-10 分，预估这个想法对北极星的影响幅度
2. **Confidence**：1-10 分，你对 Impact 估计的信心——必须有依据（过往数据/案例/逻辑）
3. **Ease**：1-10 分，实施难易度（10=半天能做，1=要重构核心）
4. **算 ICE = I × C × E**（也有用 (I+C+E)/3 的加和版，更保守）
5. **从高到低排序进入实验队列**——通常一次取 Top 3-5

**局限与不适用**：
- **比 RICE 更主观**：少了 Reach 这个客观锚，全靠估计
- **不适用于战略型决策**：ICE 是战术快速决策工具，"产品要不要转型"用 ICE 算是侮辱
- **早期 Confidence 极易膨胀**：所有人都给自己的想法 8 分，必须强制"低于 5 才能上"或"团队投票平均"
- **Ease 不等于 Effort**：Ease 包含"复杂度"而 RICE 的 Effort 是人月——团队成员能力差异会让 Ease 失真
- **常见误用**：用 ICE 给"半年期项目"打分——超过 2 周的项目应该用 RICE

**与其他理论的配合**：
- **上游配合**：增长想法池（来自竞品观察/用户访谈/数据异常）→ 喂给 ICE 排序；Kano 的 A 类候选 → 喂给 ICE 快速验证
- **下游配合**：ICE Top → 喂给 Hypothesis Testing Matrix 设计实验；喂给 MoSCoW 决定承诺
- **互替**：RICE 在 Reach 有显著差异时优于 ICE；PIE（Potential × Importance × Ease）是 ICE 的 CRO 版本

**判断要点（融会贯通信号）**：
- 当一周内要决定 5 个增长实验做哪个——ICE
- 当决策涉及 2 个月以上工作量——立即换 RICE 或更重的框架

**示例输出片段**：
> **本周增长实验 ICE 排期**
> ┌────────────────────────┬───┬───┬───┬─────┐
> │ 实验                   │ I │ C │ E │ ICE │
> ├────────────────────────┼───┼───┼───┼─────┤
> │ 首页改"价值演示"视频   │ 7 │ 8 │ 6 │ 336 │
> │ 注册流程减 2 步        │ 6 │ 9 │ 9 │ 486 │
> │ 价格页加"对比表"       │ 5 │ 7 │ 8 │ 280 │
> │ 邮件唤醒沉睡用户       │ 4 │ 5 │ 9 │ 180 │
> └────────────────────────┴───┴───┴───┴─────┘
> **决策**：本周做注册流程优化（Ease 高、信心高），下周做首页视频。

## 第三幕末决策提示

- **如果情境是"早期产品、想法多、要快速验证"**：先用 ICE 粗排 → Top 5 进入实验 → 用北极星指标做评估锚。
- **如果情境是"中后期产品、季度 Roadmap"**：Kano 分类 → RICE 评分 → MoSCoW 做承诺等级 → 北极星作为"是否服务方向"的最终检验。
