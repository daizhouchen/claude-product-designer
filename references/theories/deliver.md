# 第五幕 · 度量（Deliver）——怎么知道做对了？指标怎么定？

> **本幕目标**：把产品目标转换为可观察的信号，明确关键假设的验证方式。HEART/AARRR、反指标、假设矩阵与风险登记是按需选择的方法，不要求同时使用。局部指标修订沿用已有范围，只补足会影响这次判断的定义、计数规则或守护指标。

---

## HEART 框架 / Google 体验度量

**一句话定义**：用 Happiness / Engagement / Adoption / Retention / Task success 五个维度，把"体验好不好"翻译成可度量指标。

**出处**：Kerry Rodden, Hilary Hutchinson, Xin Fu（Google UX Research）2010 年发表于 CHI 大会 "Measuring the User Experience on a Large Scale: User-Centered Metrics for Web Applications"。Google 内部多个产品（YouTube/Maps/Search）的标准体验度量框架。

**适用情境（默认场景）**：
- 产品上线后的体验质量度量
- 体验改版前后的 A/B 对比，选择与改动有关的维度
- 跨功能/跨团队的体验对齐——HEART 给每个团队一个共同语言
- 为缺少体验衡量方式的功能建立相关指标

**核心步骤**：
1. **理解 5 维度含义**：
   - **Happiness（幸福度）**：用户主观感受——NPS / CSAT / 评分 / 满意度调研
   - **Engagement（参与度）**：使用深度——会话时长 / 页面深度 / 互动次数
   - **Adoption（采用率）**：新用户开始使用——新增激活 / 新功能采用率
   - **Retention（留存率）**：回头率——次日/7日/30日留存 / 流失率
   - **Task success（任务成功率）**：能否完成任务——任务完成率 / 时长 / 错误率
2. **每维度填 Goals-Signals-Metrics（GSM）**：目标→可观察信号→具体指标
3. **选择性投入**：不是每维度都必须监控，根据产品阶段选 2-3 个核心
4. **设阈值和报警**：每个指标定"绿/黄/红"区间
5. **季度评审 + 迭代**：HEART 数据驱动下一轮 Roadmap

**局限与不适用**：
- **不适用于 0→1 还没有用户的产品**：5 维度都需要用户基数，早期应先聚焦 Adoption
- **B 端长决策周期产品**：Retention 月级才有意义，月度看 HEART 无数据
- **维度选错代价大**：所有指标都看 = 没重点，必须选 2-3 个主要——参考 OMTM 思想
- **Happiness 最难做对**：NPS 在 B 端不灵（决策人填问卷 vs 使用人填问卷结果差异巨大），需要分角色采集
- **Task success 容易被忽视**：很多产品只看 DAU 不看任务成功率——上线一个砍流量的 bug 都看不出来

**与其他理论的配合**：
- **上游配合**：北极星指标 → 喂给 HEART 中最相关的维度；JTBD 的 Job 完成度 → 直接喂给 Task Success
- **下游配合**：HEART 异常信号 → 喂给 5 Why 根因分析；HEART 维度差异 → 喂给下一轮 ICE 实验选题
- **互替**：AARRR 在用户漏斗维度更全（多了 Referral 和 Revenue），但缺少 Task Success 维度；PULSE（Page views/Uptime/Latency/7-day active users/Earnings）更偏工程视角

**判断要点（融会贯通信号）**：
- 当只看 DAU 增长但留存或满意度未知——HEART 立即覆盖
- 当功能缺少相关指标定义时，可从 HEART 中选择有用维度，不必填满模板

**示例输出片段**：
> **HEART（B 端 AI 报表工具 v1.0）**
> ┌──────────────┬─────────────────────┬────────────────────┬────────────┐
> │ 维度         │ Goal                │ Metric             │ 阈值       │
> ├──────────────┼─────────────────────┼────────────────────┼────────────┤
> │ Happiness    │ 用户认为节省时间    │ NPS (财务专员)     │ 绿>40 红<0 │
> │ Engagement   │ 用户深度使用        │ 周均报表数/活跃用户│ 绿>5 红<1  │
> │ Adoption     │ 新用户完成首份报表  │ 7 日内激活率       │ 绿>60% 红<30│
> │ Retention    │ 用户长期回头        │ 4 周留存率         │ 绿>50% 红<20│
> │ Task success │ 报表能让老板通过    │ "通过率"           │ 绿>80% 红<50│
> └──────────────┴─────────────────────┴────────────────────┴────────────┘

## AARRR / 海盗指标

**一句话定义**：把用户生命周期分成 Acquisition / Activation / Retention / Revenue / Referral 五段漏斗，每段单独度量和优化。

**出处**：Dave McClure（500 Startups 创始人）2007 年提出，AARRR 读音像海盗呼喊得名。后被 Sean Ellis / Andrew Chen 等增长黑客社区奉为标准框架，《Growth Hacker Marketing》(Ryan Holiday, 2014) 推广至主流。

**适用情境（默认场景）**：
- 初创公司 0→1 / 1→10 阶段的增长诊断
- 增长团队的日常仪表盘 + 每周复盘
- 找增长瓶颈——哪一段漏斗转化率最差就是当前焦点
- 跨阶段融资沟通（投资人最熟悉的增长语言）

**核心步骤**：
1. **Acquisition（获取）**：用户从哪来——渠道、CPA、注册转化率
2. **Activation（激活）**：用户第一次体验到"Aha Moment"——激活率、首次价值时间
3. **Retention（留存）**：用户是否回来——N 日/周/月留存曲线
4. **Revenue（变现）**：用户付费——付费转化、ARPU、LTV
5. **Referral（推荐）**：用户推荐——K 因子、邀请激活率
6. **画漏斗 + 找最差一段聚焦**——同时优化所有段 = 没重点

**局限与不适用**：
- **B 端长周期产品**：从 Acquisition 到 Revenue 周期 6-18 个月，AARRR 月级数据无意义
- **预付费 SaaS 倒置**：Revenue 发生在 Activation 之前，标准 AARRR 顺序不适用——应改成 ARRRA 或 RARRA
- **平台型多边市场**：需要双 AARRR（供给侧 + 需求侧）
- **不适用于纯品牌型产品**：奢侈品、艺术品、内容订阅，Acquisition→Revenue 不是漏斗关系
- **常见误用**：把 AARRR 当 KPI 看板挂着，但没人对每段 owner——必须每段有专人负责
- **过度聚焦获取忽视留存**：很多团队 80% 资源投 Acquisition，但留存才是真增长基石（Retention 是 LTV 的核心）

**与其他理论的配合**：
- **上游配合**：北极星指标 → 决定哪段漏斗最关键；Journey Map → 提供漏斗每段的用户视角描述
- **下游配合**：AARRR 最差段 → 喂给 ICE 选实验；AARRR 数据异常 → 喂给 5 Why 根因
- **互替**：RARRA（重排为留存优先）适合 SaaS；HEART 在体验质量维度更深；Pirate Funnel + Cohort Analysis 组合是更现代的实践

**判断要点（融会贯通信号）**：
- 当问"我们增长瓶颈在哪"——必须漏斗化才能回答
- 当 Acquisition 涨而 Retention 跌——典型的"虚假增长"，AARRR 立即诊断

**示例输出片段**：
> **AARRR 漏斗（B 端 AI 报表工具，季度数据）**
> ┌─────────────┬────────────┬────────────┬───────────┐
> │ 阶段        │ 入口量     │ 转化率     │ 出口量    │
> ├─────────────┼────────────┼────────────┼───────────┤
> │ Acquisition │ 5000 询盘  │ 30%        │ 1500 试用 │
> │ Activation  │ 1500 试用  │ 22% ⚠️     │ 330 激活  │
> │ Retention   │ 330 激活   │ 60%        │ 198 留存  │
> │ Revenue     │ 198 留存   │ 45%        │ 89 付费   │
> │ Referral    │ 89 付费    │ 8%         │ 7 推荐    │
> └─────────────┴────────────┴────────────┴───────────┘
> **诊断**：Activation 22% 是瓶颈（行业基准 40%+）——下季度 80% 增长资源投激活流程改造，不是 Acquisition

## Counter Metrics / 反指标（守护指标）

**一句话定义**：为每个核心指标设定一个"如果这个被牺牲了就说明优化方向错了"的守护指标，防止单一指标被作弊式优化。

**出处**：Eric Ries《The Lean Startup》(2011) 提出 "vanity metrics" vs "actionable metrics" 的区分；Counter Metric 的具体概念在 Microsoft Experimentation Platform / Booking.com / Airbnb 等公司的 A/B 测试实践中成熟。Ron Kohavi 等《Trustworthy Online Controlled Experiments》(2020) 系统化 Guardrail Metrics 概念。

**适用情境（默认场景）**：
- 任何 A/B 测试设计——必须同时定义"成功指标"和"守护指标"
- 北极星指标定义时 → 同时定义反指标
- 增长激进期防止"短期数字好但长期伤客"
- KPI 考核制度——只考核成功指标会激发作弊行为

**核心步骤**：
1. **列出核心成功指标**：你想优化什么（转化率/留存/付费）
2. **想象作弊场景**：如果有人为了拉这个指标可以做任何事，最容易作弊的方法是什么？
3. **找到"作弊会引起异常"的指标**：那就是 Counter Metric
4. **设报警阈值**：Counter Metric 跌过阈值就回滚/停实验/调整方向
5. **每个核心指标至少 1 个 Counter，理想 2-3 个**——单一 Counter 也可能被钻空子

**典型对（成功指标 ↔ 反指标）**：
- 订单量 ↔ 退货率 / 客诉率
- 注册转化 ↔ 7 日留存（防止注册流程过度简化引来无效用户）
- DAU ↔ 用户单次会话时长（防止靠刷红点拉激活）
- 推送 CTR ↔ 推送关闭率
- 收入 ↔ NPS / 客诉率
- 任务完成时长 ↓（短）↔ 任务完成率 / 数据准确率
- 销量 ↔ 售后服务成本
- 内容曝光 ↔ 举报率 / 误判率

**局限与不适用**：
- **不适用于刚启动的指标体系**：还没有成功指标就先想反指标 = 本末倒置
- **反指标会被忽视**：团队 KPI 只挂成功指标 → 反指标无人 owner → 形同虚设。**必须把反指标也纳入考核**
- **过多反指标会瘫痪决策**：每个改动都触发某个 Counter Metric → 不敢动。要分"硬阈值（一票否决）"和"软阈值（警示讨论）"
- **常见误用**：把反指标和成功指标设成对立面 → 互相抵消。Counter Metric 应该是"独立维度"，不是"反方向"

**与其他理论的配合**：
- **上游配合**：北极星指标 → 必须配 Counter Metric；HEART/AARRR 每个维度 → 配对应反指标
- **下游配合**：Counter Metric 异常 → 喂给假设验证矩阵（重新评估假设）；Counter Metric 趋势 → 喂给 Risk Register（识别系统性风险）
- **互替**：Guardrail Metrics（Ron Kohavi 术语）几乎等价；Quality Metric 在体验维度类似

**判断要点（融会贯通信号）**：
- 当只看一个指标做决策——立即问 "这指标怎么被作弊"
- 当数据好看但用户反馈差——大概率正在被作弊式优化

**示例输出片段**：
> **指标守护表（B 端 AI 报表工具）**
> ┌────────────────────┬────────────────────────────────┐
> │ 成功指标           │ Counter Metric                 │
> ├────────────────────┼────────────────────────────────┤
> │ 报表生成时长 ↓     │ ①报表数据准确率 ②老板"通过率" │
> │ 7 日留存 ↑         │ ①周 NPS ②单用户报表数        │
> │ 付费转化 ↑         │ ①取消订阅率 ②客诉每千用户数  │
> │ 模板复用率 ↑       │ ①报表多样性 ②"模板撞车"投诉  │
> └────────────────────┴────────────────────────────────┘
> **硬阈值**：报表数据准确率 < 99% 立即回滚；NPS 跌 10 分以上立即评审

## 假设验证矩阵 / Hypothesis Testing Matrix

**一句话定义**：把每个产品决策当成一个"假设 → 预期结果 → 验证方法 → 决策门"的可证伪命题，进入实验前必须填完。

**出处**：基于 Eric Ries《The Lean Startup》(2011) 的"Build-Measure-Learn"循环和 Validated Learning 概念；Ash Maurya《Running Lean》（2010）的 Experiment Card；Strategyzer 的 Test Card 提供模板化结构。

**适用情境（默认场景）**：
- 任何"我们觉得 X 会带来 Y"的产品判断——都应该转成假设来验
- A/B 测试前的设计文档
- 上线前的 Pre-mortem 配套——把"会成功的理由"显式化
- 风险高/不可逆决策（定价改版、品牌重塑、架构迁移）必须先假设矩阵

**核心步骤**：
1. **写假设**：模板 "We believe [user/segment] will [behavior] when [context], because [reason]"
2. **写预期结果（Expected Outcome）**：具体到数字（"激活率提升 ≥ 5pp"），不写"会更好"
3. **设计验证方法**：MVP / A/B / 用户访谈 / 数据回测 / Wizard of Oz / Smoke Test——选成本最低的
4. **定决策门（Decision Gate）**：
   - 达到预期 → 投入做
   - 部分达到 → 改进后再验
   - 未达到 → 砍掉或转方向
5. **记录学习**：不管成败都要回写矩阵——失败的假设比成功的更值钱

**局限与不适用**：
- **不适用于无法量化的判断**：纯审美/品牌方向的判断很难"达到/未达"二元化
- **不适用于战略级决策**：战略层判断周期长、可逆性差，不能用快速实验验证——应用情景规划（Scenario Planning）
- **常见误用**：写出来的"假设"是事后说服文 → 永远成功——必须前置写好预期，不能事后改
- **未来偏见**：把 P-Value 当真理 → 统计显著性不等于业务显著性，5% 提升即使显著也可能不值得做
- **Confirmation Bias 风险**：设计实验时倾向证实而非证伪——必须设计"什么数据会让假设被证伪"

**与其他理论的配合**：
- **上游配合**：反向假设 → 提供"致命假设"作为优先验证项；Lean Canvas 的"待验证假设"→ 直接喂给矩阵；ICE → 提供哪个假设先验
- **下游配合**：验证通过的假设 → 喂给 Story Map / Roadmap 落地；验证失败的假设 → 喂给 Risk Register（记录已知不可行）
- **互替**：Strategyzer Test Card 是单假设的卡片化模板；Experiment Card / Learning Card 在 Lean Startup 体系是标准工具

**判断要点（融会贯通信号）**：
- 当听到"我觉得用户会喜欢"——立即转成假设矩阵
- 当 A/B 实验设计中"成功标准"没事先写明——假设矩阵立刻补

**示例输出片段**：
> **假设验证矩阵（注册流程简化实验）**
> ┌─────────────────────┬─────────────────────────────────────────┐
> │ 假设                │ 财务专员看到"3 步完成首份报表"的引导对    │
> │                     │ 比传统 7 步表单，激活率提升 ≥ 8pp        │
> │                     │ ，因为他们最痛的是"上手前的繁琐"        │
> ├─────────────────────┼─────────────────────────────────────────┤
> │ 预期结果            │ 实验组激活率 22% → 30%+（绝对值 +8pp）  │
> │                     │ Counter: 30 日留存不低于对照组 -2pp     │
> ├─────────────────────┼─────────────────────────────────────────┤
> │ 验证方法            │ A/B 50:50, 双周, n ≥ 1000 / 组          │
> ├─────────────────────┼─────────────────────────────────────────┤
> │ 决策门              │ ≥ +8pp 且留存守护通过 → 全量            │
> │                     │ +4 to +8pp → 改进表单后再验             │
> │                     │ < +4pp 或留存跌 > -2pp → 砍掉，假设错   │
> ├─────────────────────┼─────────────────────────────────────────┤
> │ 学习沉淀（事后填）  │ [上线后回填]                            │
> └─────────────────────┴─────────────────────────────────────────┘

## 风险登记表 / Risk Register

**一句话定义**：把所有"还没发生但可能发生"的负面事件登记成表，定责任人、应对方案和触发条件。

**出处**：源于项目管理学科（PMI PMBOK 把 Risk Register 列为标准产物）；产品/产品风险管理由 Marty Cagan《INSPIRED》和 Teresa Torres《Continuous Discovery Habits》(2021) 提倡在产品发现期就建立 Risk Register。

**适用情境（默认场景）**：
- 任何 0→1 项目立项时——和 Lean Canvas 同步建立
- 改版/迁移/重构等高风险动作前
- 跨团队依赖项目（依赖方延期是常见风险）
- 季度评审的固定环节——回顾老风险 + 登记新风险

**核心步骤**：
1. **识别风险**：四类风险全列——①价值风险（用户不要） ②可用性风险（用户不会用） ③可行性风险（技术做不出） ④商业风险（不可持续）
2. **每条风险填 6 列**：Risk ID / 描述 / 发生概率 / 影响等级 / 应对策略 / Owner
3. **应对策略分四种**：Avoid（避免）/ Mitigate（减轻）/ Transfer（转移）/ Accept（接受）
4. **画 Risk Matrix**：概率 × 影响 = 优先级。高概率+高影响 = 红区，必须立即处置
5. **定期更新**：每月评审，已发生的风险转入"已实现"，新出现的登记进来

**局限与不适用**：
- **不适用于个人小项目**：太重，1 个人的 Side Project 心算就够
- **容易变成"满足合规的文档"**：写完挂着无人看 → 没有真正起作用。必须每月评审 + Owner 负责
- **未知的未知**：Risk Register 只能登记"想得到的风险"，对真正的黑天鹅无效——所以需要配合反向假设和蓝军演练扩展认知边界
- **过度悲观陷阱**：每个角度都登记成红区 → 风险疲劳。要严格按概率×影响打分，不允许"我觉得很严重"代替评估
- **Owner 不明的风险等于没有**：必须每条 Risk 有一个具体的人负责，不能挂在"团队"名下

**与其他理论的配合**：
- **上游配合**：反向假设的"致命失败" → 直接喂给 Risk Register；Lean Canvas 每格的不确定 → 喂给 Risk Register
- **下游配合**：高优先级 Risk → 喂给假设验证矩阵（设计实验消除）；Risk 触发 → 喂给应急响应/复盘流程
- **互替**：Pre-mortem 是 Risk Register 的会议化版本，更深更轻；SWOT 分析在 W+T 维度类似但更宏观；FMEA（Failure Mode and Effects Analysis）在工程领域更结构化

**判断要点（融会贯通信号）**：
- 当团队反复说"应该不会出问题吧"——立即 Risk Register
- 当一个风险发生两次都没人 own——制度问题，而非个人问题

## 第五幕末决策提示

- **如果情境是"产品刚上线、要建度量体系"**：HEART + AARRR 双框架同步建立（HEART 看体验，AARRR 看增长），每个核心指标必配 Counter Metric。
- **如果情境是"要做 A/B 实验"**：假设验证矩阵 + Counter Metrics 是入场券——没填这两个不允许开始实验。
- **如果情境是"高风险/不可逆决策"**：Risk Register + 假设验证矩阵 + Pre-mortem 三件套，缺一不行。
- **如果情境是"老指标在涨但用户反馈差"**：立即用 Counter Metrics 做反向诊断，多半正在被作弊式优化。
- **核心警告**：**没有 Counter Metric 的成功指标会被作弊式优化**，没有 Risk Register 的项目会在同一个坑里栽两次，没有假设矩阵的实验是"事后讲故事"。本幕产物的硬指标是"①HEART/AARRR 度量表 ②每核心指标 1+ Counter Metric ③上线前假设矩阵 ④Risk Register 含 Owner"。第五幕不是终点——它是下一轮第一幕的起点。
